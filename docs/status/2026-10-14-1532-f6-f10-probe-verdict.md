# F6 / F10 probe: ship nothing (reasoning input is a no-op, temperature 1.0 does not help)

Decision record for issue #145, items 3 (F6, in-loop reasoning) and 4 (F10,
temperature). gpt-oss-120b on Cerebras, `@ai-sdk/openai-compatible` 2.0.82,
ai 6.0.306. Live spend about $0.60.

## The question

In live Wave runs, gpt-oss often writes a tool call as JSON text in the
prose instead of making a real tool call. On main this showed up in 5 of 9
runs, and 2 of 9 runs failed a Turn (#145, #164). OpenAI's gpt-oss guidance
names two levers:

- **F6:** keep the reasoning (`analysis` channel) between tool Steps within
  a Turn. `cerebrasToolLoopPrepareStep` strips it before every Step.
- **F10:** sample at temperature 1.0. Nalu runs the Wave loop at 0.3.

## Step 1: F6 is not feasible on Cerebras

The strip exists because the adapter sends reasoning back as
`reasoning_content`, and Cerebras rejects that field. Cerebras returns
reasoning as `message.reasoning`. Its docs show `reasoning` as the input
field, but only for Qwen.

The official `@ai-sdk/cerebras` (2.0.88, the `ai-v6` line, built on the same
adapter 2.0.82) does one thing for this: its `transformRequestBody` renames
`reasoning_content` to `reasoning`. `createOpenAICompatible` takes the same
hook, so Nalu would need no new package for it.

Raw calls, same tool-call chain (user, assistant tool call, tool result),
`reasoning_effort: low`:

| Assistant tool-call message carries | HTTP | prompt_tokens | Model recalls a code word from it |
| --- | --- | --- | --- |
| nothing | 200 | 199 | no |
| `reasoning` (~500 tokens) | 200 | 199 | no |
| `reasoning` (~1,100 tokens), earlier call | 200 | 204 (204 without) | n/a |
| `reasoning_content` | 400 `wrong_api_format` | n/a | n/a |
| `thinking` | 400 `wrong_api_format` | n/a | n/a |
| the same text as `content` | 200 | 682 | yes |

- Cerebras accepts `reasoning` on input, then drops it for gpt-oss. The
  prompt does not grow and the model cannot see it. Renaming the field
  would be a silent no-op, and so would switching to `@ai-sdk/cerebras`.
- The same text in `content` does reach the model (+483 tokens, recall
  works). Which harmony channel Cerebras renders it on is unknown. This
  route was not tested in the loop; see "Open lever".
- Prompt cache: persisted rows hold no reasoning. `toolStepRows` stores tool
  calls and tool results, and the Turn stores its prose. So the Context's
  prefix is the same either way. Kept reasoning would only lengthen the
  in-loop Steps of one Turn.

Arms B (F6) and D (F6 + F10) were skipped.

## Step 2: the A/B

Method: `src/server/routers/wave.live.test.ts`, 3 runs per arm, run in
pairs (one A beside one C) between 15:26 and 15:32 BST, so provider drift
hit both arms. Arm C set the Wave mid-turn agent's temperature to 1.0
through a probe-only env toggle; scoping and the Wave close stayed at 0.3.
A probe-only stderr line logged each tool-loop attempt: Steps, tools, gate
result, and the head of any JSON in the prose. Both edits were reverted.

"JSON text" counts attempts that the gate failed for a raw JSON object. Turn
numbers are Wave turns (1 to 9 are mid-turns).

- One more C run, before the probe log existed, passed with no failed
  attempts. Its 13 Wave Steps equal the minimum for its tool pattern, so no
  attempt failed.
- No in-loop tool call was invalid in any run. No attempt that passed the
  gate held JSON.
- Grading showed no difference. Every close that graded a free-text answer
  gave q5 (A2, C1, C2).
- The final mid-turn quiz (T9): A2, C1 and C2 used `presentQuestionnaire`.
  A1 and A3 dumped JSON once, then asked the quiz in prose on the retry, so
  the close had nothing to grade.

## Verdict

**Ship nothing. Keep the reasoning strip and temperature 0.3.**

- **F6 (#145 item 3):** not feasible. Cerebras ignores `reasoning` on input
  for gpt-oss, so the strip loses nothing today. Re-test trigger: Cerebras
  documents reasoning input for gpt-oss, or the raw check above shows
  `prompt_tokens` rising when `reasoning` is sent.
- **F10 (#145 item 4):** temperature 1.0 does not cut JSON text. It doubled
  the JSON-text attempts (6 vs 3) and failed a Turn, which baseline did not.
  Three runs per arm cannot prove 1.0 is worse, but they rule out a clear
  win.
- **Where the problem is:** 7 of 9 JSON-text attempts were the bare
  `{"questions": …}` object, which is `presentQuestionnaire`'s input written
  as text. Only 1 was the `{name, arguments}` envelope. Twice the model
  called a tool and also dumped the quiz JSON in its prose (C2 T2, C3 T1).
  All 9 held a quiz the model meant to pose. In A1 T4 and C3 T1 the learner
  had not asked for one. That points at the quiz tool contract and prompt,
  not at sampling. The gate held every time: nothing leaked past it.

## Open lever (untested)

Reasoning sent as the tool-call message's `content` does reach gpt-oss on
Cerebras. If Cerebras renders that `content` on the `analysis` channel (the
Hugging Face gpt-oss template does), this is a real F6 route. Two caveats:
a Step's own prose already rides in that field, and the rendered channel is
unknown. It needs its own probe before any loop change.

## Side finding: a scoping run lost to runaway reasoning

One A run was excluded. It failed in scoping, before the Wave. The
scoping-close call spent exactly 40,000 output tokens, 39,997 of them
reasoning, then threw `NoOutputGeneratedError`. `executeTurn` retries only
`NoObjectGeneratedError`, so the Turn failed on attempt 1 of 3, with no
retry. The arms do not touch scoping. One sighting so far.
